# ContextFlow 评测

评测体系回答三类问题：**快**（端到端时间与工具成本）、**准**（状态 / Agent / 工具 / RAG 证据 / 结果是否正确）、**狠**（覆盖、长链路、安全边界）。

## 四条不可违背的纪律

跑任何正式对比之前先确认这四条。违反其中任何一条，结果都不能写进材料：

1. **环境固定**：同一设备、同一 OpenClaw / MTClaw 版本、同一上游模型与参数、同一固定资料、同一超时。
2. **每轮新 session + 独立临时目录**：隔离历史状态，否则上一轮的残留会污染这一轮。
3. **轮次交替顺序**：奇数轮 Native → ContextFlow，偶数轮反向。只跑一种顺序，测出来的差异可能来自先后而不是方案本身。
4. **口径诚实**：ContextFlow 多出来的导入、确认、撤销等工作必须同时报出。当两个方案的工作量不等价时，不能只报对自己有利的那一个数字。

> 第 4 条是这套评测里最容易违反、也最伤可信度的一条。任何"加速比"或"优于"的结论，先问一遍：**两个方案做的事情是同一件事吗？**

## 报告产出

每次正式运行在 `benchmark/reports/` 生成 JSON 与 Markdown 两份：

- `contextflow-benchmark-*`：9 项专项确定性 Benchmark
- `unified-ab-*`：A/B 端到端报告

**脱敏规则**：报告只保留 Router 工具名称与统计，**不复制工具参数与完整结果**。真实文件路径、会议原文、密钥只留在本机 SQLite 审计表中，不进入报告。

## 失败归因

一个 Case 没过时，按顺序看：

1. 读该轮的脱敏 Router Trace，对比期望路径与实际路径。
2. 分清是**代码没实现规格**还是**规格本身写错了**——两者改的东西完全不同。
3. 如果失败集中在同一类（例如 RAG），先怀疑工具描述区分度不足或候选集过大，而不是逐个修 Case。
